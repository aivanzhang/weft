# Proposed demonstration and evaluation design

This is a proposed implementation plan, not an implemented system or an official hackathon requirement. It interprets the [judging rubric](../sources/participant-guide.md) and the user's application.

## One result worth demonstrating

A policy exploits or relies on an inaccurate rule in a generated sorting simulator. Physical observations contradict that rule. A Meta model diagnoses the mismatch and proposes a bounded repair. An independent evaluator rejects invalid changes and accepts a correction. A policy trained in the corrected environment improves on held-out physical trials.

One task, a small discrete action space, a small number of objects, one or two measurable mismatch types. Do not promise arbitrary simulator synthesis, photorealistic physics, a general robotics platform, or a broad library within this event.

## Suggested system boundaries

```text
task specification + generation observations
                  |
                  v
Meta model -> structured environment specification -> sandboxed executable v0
                                                       |
                                                       v
                                                agent rollouts
                                                       |
repair observations -> discrepancy report -> Meta diagnosis + candidate patch
                                                       |
                                                       v
                              fixed evaluator -> reject OR version v1
                                                       |
                                                       v
                                matched policy learning + final held-out trials
```

Generation observations, repair observations, and final evaluation trials are different data partitions. The repair agent never receives the final held-out labels or evaluator write access.

## Minimum components

1. **Task/evidence schema.** Stable object IDs, observed state, chosen action, resulting state, task outcome, observation confidence, episode ID, source, time, and file hash. Preserve the raw observation alongside any model interpretation.
2. **Bounded environment interface.** Explicit reset/step contract, legal actions, state invariants, terminal conditions, and fixed task-success definition. Version every environment artifact.
3. **Generator.** Meta produces inspectable executable rules or a structured specification compiled into rules. Record which scaffolding was supplied by us versus generated by the model.
4. **Rollout and policy learner.** Use a small measured policy-learning method appropriate to the task. A tabular learner is sufficient if the state/action space supports it. Do not call model planning or hardcoded routing “RL training.” Report the actual algorithm.
5. **Discrepancy detector.** Compare predicted transitions against observed transitions and detect reward/task-success disagreement. Label epistemic uncertainty rather than forcing guesses.
6. **Repair loop.** Bounded attempts and tool budgets. Meta reads evidence, proposes a diagnosis, modifies allowlisted environment code or parameters, and receives development-test feedback.
7. **Independent evaluator.** Fixed invariant tests, regression episodes, and physical outcome checks. The repair process cannot weaken success conditions, rewrite observation labels, or replace the grader.
8. **Trace viewer.** Side-by-side observation, prediction, patch, evaluator decision, and before/after metrics. Long-running jobs execute off the UI thread and can be cancelled.

## Meta tooling roles — proposed, not tested

Official [model list](../sources/meta-docs-models.md) and [quickstart](../sources/meta-docs-quickstart.md) were checked on October 26, 2026. Availability and limits still require a real account-level smoke check before implementation commitments.

- **Muse Spark 1.3:** candidate for multimodal evidence interpretation and routine structured reasoning/tool steps.
- **Muse Wonder:** candidate for more difficult code diagnosis and targeted repair. Use only when it earns the latency/cost.
- **Muse Spark Open / Muse Glimmer:** optional actual runtime for the open-weight award or a comparison. Do not add a second inference deployment solely for a badge if it threatens the core demo. Baseten's event-specific identifier is `meta-models/muse-spark-open-1026`.
- **SAM 3.1:** optional segmentation if it materially improves object/state observations. Avoid making perfect perception a prerequisite for proving the repair loop.
- **Muse Code:** optional development tooling, not a substitute for meaningful model use inside the submitted system.

No API key was inspected, no model call made, no spend incurred, and no model superiority established during this research pass. Start with one real structured-output/tool-use smoke test when implementation is authorized.

## Evidence and metrics

| Metric | Operational definition | Report with it |
| --- | --- | --- |
| Transition prediction error | Mismatch between predicted and observed next-state fields on held-out trials; use categorical error for discrete state or an explicitly defined numeric loss | Trial/episode count, state fields, conditions, uncertainty, before/after versions |
| Simulator exploit frequency | Share of audited rollouts with high simulated reward but a violation of immutable task success or physical constraints | Rollout budget, matched seeds, exploit detector definition, example traces |
| Simulation-to-reality performance gap | Simulated success rate minus physical success rate for the same frozen policy and comparable initial conditions | Both rates separately, denominators, trial distribution, confidence intervals where justified |
| Repair reliability | Accepted repairs, rejected repairs, regressions, unresolved mismatches | Attempt budget, test-set identities, independent checks |
| Practical cost | Time and model/API cost for generation, diagnosis, repair, evaluation, and policy learning | Median/tail timings if enough runs, hardware/provider, rate limits, failures |

Split by complete episode/condition, not adjacent video frames. Otherwise near-identical frames leak across partitions. Preserve a final untouched evaluation set; repeated development gating needs its own validation set. Re-running a frozen final evaluation for reporting is different from using its feedback to tune the system.

Useful comparisons: unrepaired generated simulator; repaired simulator; a simple parameter-fit baseline where applicable. If measuring trained-policy improvement, use comparable learning budgets and trials, and distinguish improved environment prediction from improved real-world control.

There are no results yet. Select realistic sample counts after checking physical trial time; show uncertainty and failed trials rather than inventing statistical strength.

## Physical task choices to settle

The user proposed tabletop sorting, but available hardware and data have not been specified. Do not assume a robot exists or buy one.

- A person executing discrete instructions can supply physical transition data. Clearly label the person as actuator; the claim is environment correction, not autonomous robot control.
- A robot provides stronger end-to-end control evidence if already available and reliable, but hardware setup should not dominate the event.
- Recorded physical trials can support prediction validation. They do not by themselves prove a newly trained policy succeeds on new physical rollouts.
- A synthetic “real” simulator is useful for development and controlled bug tests only. Label it synthetic; it cannot establish real-world transfer.

Candidate mismatch classes to choose from, not promises: bin capacity, unavailable moves, object-dependent grasp/slip probabilities, occlusion-dependent uncertainty, or a reward shortcut. Prefer a mismatch visible to a nonexpert and measurable with safe, short trials.
