# Weft v1 — the first trainable world

**Prove the complete loop on a small physical task family.**

One supported video should produce a shared, interactive physical world and an explicit RL task. An agent should be able to learn inside it, while an independent report shows what the world explains, what it assumes, and where it fails.

Scope updated October 27, 2026. This is the **first product milestone**, not a retrospective description of the existing single-ball fixture.

## Proposed first scope

The long-term architecture remains broad. The first milestone limits the number of unknowns while preserving every stage of the video-to-RL loop.

| First version | Later expansion |
| --- | --- |
| A short, continuous physical video | Long recordings, cuts, and scene changes |
| Rigid objects, supporting surfaces, and obstacles | Articulated animals/humans, cloth, fluids, and other deformable materials |
| One controlled entity | Multiple independently acting entities |
| One shared coordinate system, timebase, and physical simulation | Larger scenes and more varied interaction mechanisms |
| Simple geometry with meaningful interactions | Detailed photorealistic reconstruction |
| One supported task family | Broad task discovery across unrelated videos |
| Bounded candidate repair and numerical fitting | Larger adaptive or learned search |
| Physical environments | Website/workflow environments with UI, notification, and application state |

**Recommended starting class:** a few interacting rigid objects in a short, fixed-camera scene—for example, a pusher, movable object, support surface, and obstacle. Tabletop pushing/sorting versus ball collisions remains an open scene choice, not a decision implied by the current fixture.

## What exists today—and what does not

The repository documents a working local iteration foundation: video measurement, a shared numerical simulator, bounded parameter repair, protected checks, an evidence viewer, and tabular RL. Its supported profile is one isolated yellow ball moving horizontally. The added controls and parking objective are authored, not extracted from the video.

That fixture verifies pipeline mechanics. It does **not** establish multi-object reconstruction, metric 3D recovery, general task extraction, physical transfer, or live Meta-model integration. An optional Meta adapter exists but is not live-verified. ## The end-to-end experience

1. **Provide one video.** Record its origin, rights, checksum, timing, and supported-input checks.
2. **Inspect the evidence.** See object identities, motion, interactions, physical hypotheses, and unknowns.
3. **Enter the shared world.** Replay the demonstration from the original view; inspect geometry from another view, with inferred details labeled.
4. **Change an action.** Use the declared control interface and observe a new simulation outcome.
5. **Inspect a repair.** Compare a baseline and candidate under the same fixed checks; see accepted and rejected changes.
6. **Train an agent.** Learn the declared task and compare against simple baselines under matched conditions.
7. **Export the result.** Preserve the world, task, evidence, configurations, scores, run history, and reproducible commands.

No clip-specific simulator edits should be needed for an unseen clip within the supported family. Any manual measurement, annotation, tracking adjustment, or supplied task intent must be counted as intervention rather than hidden from the “one video” claim.

## Minimum deliverables

| Stage | Required v1 output | Acceptance evidence |
| --- | --- | --- |
| A · Physical understanding | Multiple relevant objects, persistent identities, states, events, and physical relationships with evidence status | Independently checked tracks/events; support/contact mechanisms; documented scale and camera assumptions |
| B · Shared reconstruction | One executable world with coherent geometry, contacts, constraints, and bounded controls | Original-view replay, alternate-view inspection, and changed-action rollouts without reference-trajectory playback |
| C · Candidate improvement | Bounded hypotheses and a protected accept/reject loop | An interpretable baseline/candidate comparison, rejected invalid changes, and a complete decision ledger |
| D · Evaluation | Separate reconstruction, physics, intervention, robustness, and task scores | Frozen criteria, explicit unavailable measurements, negative controls, and preserved failures |
| E · Learning | An explicit task contract and an actual trained policy | Matched baseline trials, independent success checks, training/evaluation seeds, and learning curves or equivalent records |
| Evidence viewer | A readable local comparison of source, simulation, object state, candidate changes, and results | Navigable artifacts, responsive bounded updates, and a clear distinction between replay and live simulation |

Keep a stable interface between modules so perception, reconstruction, and model providers can improve without redefining the evaluator.

## Physics and evaluation coverage

Apply the [full scorecard](goal.md#d-evaluate-fidelity-physical-validity-and-usefulness) proportionately to the supported scene. Unsupported mechanisms must remain explicit exclusions; v1 does not need fluid simulation to have a sound evaluation design.

The following are proposed Weft checks, not claims of having run or reproduced WorldBench:

| Test family | Minimum meaningful check |
| --- | --- |
| State and contact | Motion responds to the selected dynamics; contacts occur at compatible positions and times; forbidden crossings fail |
| Support and constraints | Removing a declared support changes motion appropriately; joint or actuator bounds hold where those mechanisms are supported |
| Visibility and geometry | Objects retain identity through brief supported occlusion; changing a render camera does not modify physical state |
| Parameter evidence | Each parameter has units and observed/inferred/assumed/unknown provenance; quantitative recovery is scored only when independently identifiable |
| Stability and robustness | Repeated reset/step runs remain finite; known edge cases fail explicitly; tests cover changed initial conditions and multiple seeds |
| Task integrity | An invalid shortcut cannot earn task success merely by collecting reward; the evaluator is not writable by repair |
| Practical cost | Record manual interventions, generation/repair/training time, resource use, and external charges—including failed attempts |

Use analytic or synthetic fixtures to test mechanisms, then a licensed real video to exercise the actual pipeline. Preserve the distinction: a passing controlled fixture is not a measured real-world intervention.

For evaluation beyond the construction clip, select fresh videos or physical trials before tuning. If the full source has been inspected by A, score it as reconstruction. Do not reclassify part of that same exposed recording as a final holdout.

## Build order and dependencies

**Evaluation contracts → A and a minimal B → E → C's automated improvement loop.**

| Milestone | Work | Ready when |
| --- | --- | --- |
| 0 · Freeze the testable problem | Choose one interaction family; specify actors, controls, task, evidence boundaries, and provisional tolerances | A source and an independent scoring plan exist; uncertainty and unsupported cases are written down |
| 1 · Establish A and D | Implement the physical scene/evidence contract and perception; prepare fixed tests in parallel | Objects and relationships are inspectable; bad candidates fail known checks |
| 2 · Make B interactive | Generate a minimal shared physical world | It reproduces relevant events and responds to changed actions without scripted object playback |
| 3 · Complete E | Add the task interface, learner, and baseline evaluation | Learning is measured against independent success on matched trials |
| 4 · Close C's repair loop | Add diagnosis, bounded proposals, and regression rejection | Candidate selection is reproducible and cannot weaken the benchmark |
| 5 · Validate and present | Run fresh supported inputs, inspect failures, package the local demo and evidence | Results are reproducible, limitations are visible, and supported claims have artifacts |

Independent fixture preparation, perception work, and interface work can proceed concurrently after their contracts are agreed. Do not let several workers modify the same files, duplicate expensive inference, or compete for the same output directories.

## Resource and cost discipline

- Start with a small local learner and the simplest adequate physics representation. Do not provision a GPU service or train a foundation model as a default.
- Decode each source once, reuse prepared measurements where valid, and cache by source/configuration identity.
- Start with one world; introduce a small candidate population only when it tests a real ambiguity. Bound repairs and stop when the declared budget or evidence limit is reached.
- Before paid model execution, record current provider pricing, input volume, output limits, retries, evaluation calls, compute, storage, and a projected one-time/recurring envelope. Credential presence is not spending authorization.
- The existing local fixture has no external API/cloud charges. That is not a cost estimate for the expanded multi-object or Meta-enabled version; consult [execution bounds](docs/v1-cost-and-scope.md).
- Preserve failed runs and source provenance. Use fresh output directories, bounded process lifetimes, and explicit cancellation; do not overwrite evidence or silently substitute mocks for failed model calls.

## Definition of done

The first product milestone is complete when:

- A previously unseen video **within the declared supported family** produces a multi-object world and task without per-video code edits.
- Object relationships are grounded in physical mechanisms and supported evidence; uncertain parameters remain visibly uncertain.
- Original-view reconstruction passes predefined tolerances; changed actions produce meaningful, bounded outcomes in the same world.
- Candidate selection preserves the evaluator and records failures, regressions, and rejected proposals.
- An actual learning algorithm improves task performance against appropriate baselines under a fixed evaluation setup; any failure to improve remains a reported result, not a rewritten benchmark.
- The run can be inspected and reproduced from pinned source, code, assets, settings, model records where used, and seeds.
- The report separates observed reconstruction, synthetic checks, simulated generalization, and any independently measured physical transfer.
- Model usage is accurately reported. Meaningful, live-verified Meta use is a separate requirement for presenting the prototype as a Meta-powered hackathon entry.

Start with one complete smoke run, then evaluate additional fresh clips within the same family before claiming reliable video-to-environment generation. A single hand-tuned example does not establish that capability.

## Decisions still open

1. **Interaction family:** tabletop pushing/sorting or another tractable rigid-body interaction.
2. **Controlled entity and goal:** what the agent can change and what success means.
3. **Calibration:** whether the chosen input supports metric physics or only relative reconstruction.
4. **Independent evidence:** what fresh clips, measured parameters, or physical interventions are available.
5. **Meta role and budget:** which model decisions materially affect the output and how they will be verified.

These choices narrow an implementation, not the long-term product. Contract work and controlled evaluation fixtures can proceed while they are settled.
